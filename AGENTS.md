## Superpowers

- Superpowers является рабочим процессом проекта. В начале задачи используй
  `superpowers:using-superpowers`, затем подходящие skills по ситуации.
- Ошибка: `systematic-debugging` до исправления. Новое поведение:
  `brainstorming` для неясных решений. Значимая логика и регрессии:
  `test-driven-development` с проверками по риску из §10.
- Перед утверждением о готовности: `verification-before-completion`.
  Для значимого изменения и перед мёрджем: `requesting-code-review`;
  замечания разбирай через `receiving-code-review`.
- Требование владельца: не создавать слайсы, спецификации и файлы планов
  по умолчанию. Критерии, шаги и решения веди в чате. Документ создаётся только
  по запросу или отдельной договорённости. Эта настройка важнее шаблонов skills.
- Не копируй skills в репозиторий и не закрепляй абсолютные пути их установки.
  Если skill недоступен, сообщи об этом; не заявляй о его применении.

## Работа и guardrails

- Одна задача, один сфокусированный diff. Работай в отдельной ветке;
  worktree нужен при занятом checkout или параллельной работе.
- Следуй существующей вертикали: роут → policy → сервис → репозиторий.
  Эталон K5: `src/routes/(portal)/portal/profile`.
- TypeScript strict, без `any`. До 250 строк на файл и 40 на функцию.
  Домен без IO; сервисы и репозитории наследуют `BaseService`, `BaseRepository`.
- Весь вход валидируется Zod на сервере. Проверяй право каждого действия;
  портальные данные фильтруются по `ActorContext.counterpartyId`.
  Закрытые цены отсекаются в `select` и DTO, не в UI.
- Деньги в целых копейках, поля БД с `_minor`. Изменения пишутся в аудит,
  переходы заявки в историю. Используй существующие UI-примитивы и токены.
- Не печатай секреты и ПДн. Рабочие БД, файлы и внешние сервисы не являются
  тестовыми фикстурами. Не удаляй данные и не переписывай git-историю вне запроса.
- Закрытые продуктовые решения из §21 не возвращаются инициативой агента.
  Миграции только `pnpm db:generate`; `drizzle/` руками не правь.

## CONTRACT GAP

Не хватает таблицы, поля, типа, топика или пропса примитива: останови зависимую
реализацию, выдай блок и дождись решения владельца и обновления ядра с версией.
Независимое исследование можно продолжать; временную заглушку не пиши.

```text
CONTRACT GAP
Нужно: <таблица/поле/тип/топик>
Зачем: <какой сценарий задачи блокируется>
Предлагаемая форма: <точное определение в терминах Drizzle/TS>
Влияние: <какие части системы затронет>
```

## Проверки и история

- Тесты выбирай по критериям и риску. Порога покрытия нет. Не добавляй дубли
  ради количества; используй существующие проверки.
- В ходе задачи запускай затронутые проверки. Перед мёрджем полный гейт §11.1.
  Сборку и e2e не запускай параллельно, чужой сервер ради порта не останавливай.
- Делай небольшие логические коммиты, добавляй конкретные файлы.
  Формат `type(scope): summary`, английский императив со строчной буквы,
  summary до 50 символов, без точки. Типы `feat|fix|test|refactor|chore|docs`,
  scope `auth|catalog|request|stock|payroll|portal|crm|queue|ui|ci`.
- Автор из git config: `Sobol17 <sobolinskiii@mail.ru>`, без `--author`,
  соавторов, генераторных подписей, упоминаний моделей и промптов, эмодзи.
- Комментарии кода и PR по-английски, документация и UI по-русски.
  Комментарий объясняет причину. Без TODO и закомментированного кода в мёрдже.
  Проза по `stop-slop`: конкретно, активно, без филлеров, em-dash и эмодзи.
- В итоге укажи изменения, выполненные команды и результаты, ограничения,
  ветку и коммиты. Незапущенную проверку не называй пройденной.

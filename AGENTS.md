# Инструкции проекта

Проект: B2B-портал и CRM мастерской «Ангел». Единственный разработчик и
владелец решений: Sobol17. Общение с владельцем по-русски.

## Источники и начало работы

- Перед первым действием в сессии прочитай [tech.md](tech.md). Это источник
  контрактов, архитектуры, прав и границ продукта. При расхождении с кодом прав он.
- Проверь `git status --short --branch` и текущий diff. Сохраняй чужие изменения,
  незакоммиченные файлы, рабочие деревья и запущенные процессы.
- До редактирования прочитай вложенные `AGENTS.md` для затрагиваемых каталогов,
  даже если сессия стартовала из корня. Они дополняют эти правила.
- Для процесса прочитай [docs/agent-workflow.md](docs/agent-workflow.md).
  Для многошаговой работы используй [PLANS.md](PLANS.md).
- Статус слайсов берётся из `tech.md` §14 и проверяется по коду и git.
  Старые чекбоксы плана не доказывают, что работа выполнена или ещё не начата.

## Выполнение задачи

- Одна задача, один сфокусированный diff, один PR. Эталон вертикали:
  `src/routes/(portal)/portal/profile` (K5).
- Уточняй только то, что меняет требования, контракт или требует решения
  владельца. Обычные обратимые действия в согласованной задаче выполняй сам.
- Работай в отдельной ветке. Не смешивай новую задачу с текущим слайсом.
  Worktree нужен при параллельной работе или занятом checkout; не переноси туда
  секреты и рабочую БД автоматически.
- Проверки запускай по мере работы. Перед мёрджем обязателен полный локальный
  гейт `tech.md` §11.1. CI запускается вручную, CD нет.
- Skills помогают работе, но проект не требует установки конкретного набора.
  Если нужного skill нет, следуй этим файлам. Не выдумывай отсутствующий инструмент.

## CONTRACT GAP

Не хватает таблицы, поля, типа, топика или пропса примитива: останови зависимую
реализацию и выдай блок. Не добавляй контракт или временную заглушку сам.

```text
CONTRACT GAP
Нужно: <таблица/поле/тип/топик>
Зачем: <какой сценарий слайса блокируется>
Предлагаемая форма: <точное определение в терминах Drizzle/TS>
Влияние: <какие слайсы затронет>
```

Дождись решения владельца, обновления нужного раздела `tech.md` и версии ядра.
Независимые проверки и исследование можно продолжать. Миграции генерируются
только `pnpm db:generate`; файлы `drizzle/` руками не правь.

## Обязательные ограничения

- TypeScript strict, без `any`. До 250 строк на файл и 40 на функцию.
- Роут → policy → сервис → репозиторий. Сервисы наследуют `BaseService`,
  репозитории `BaseRepository`. Домен чистый, без IO и SvelteKit.
- Вход валидируется Zod на сервере. Право проверяется на каждое действие до
  разбора формы; портальные запросы фильтруются по `ActorContext.counterpartyId`.
- Цены отсекаются в `select` и DTO по §8.1, §19. Проверяется тело ответа.
- Деньги в целых копейках, поля БД с `_minor`, округление через общие утилиты.
- UI строится из `lib/ui` на shadcn-svelte. Контракты примитивов в §9,
  токены в `src/app.css`, макеты портала в `ui/` и §18. Вторую UI-библиотеку,
  свои таблицы и модалки не добавляй.
- Изменяющие действия пишутся в аудит; переходы заявки в историю статусов.
  Тесты следуют критериям приёмки (§10), домен покрыт минимум на 90% строк.
- Секреты только в локальном окружении. Пути БД и файлов берутся из конфига.
  Не печатай содержимое `.env`, токены, пароли и персональные данные.
- Закрытые решения в §21 обязательны: нет брака, переделок, приостановки,
  рекламаций, отказа при доставке, самовывоза, предоплат и переплат;
  нет QR, документов/PDF, норм расхода и автосписания, исполнителей заявки.
- PWA только для установки и Web Push: без `fetch` в SW, Cache Storage и офлайна.
  Push через VAPID, почта только для доступа. Канал `email` в события не возвращай.
- Стенд: Docker и Caddy, ручной деплой по `docs/deploy.md`. Не добавляй CD.

## Проверки и сдача

Команды и безопасный запуск описаны в `docs/agent-workflow.md`:
`pnpm lint`, `pnpm check`, `pnpm test:unit`, `pnpm test:e2e`, `pnpm build`,
миграции и сид на чистой временной БД, health собранного приложения.
Сборку и e2e не запускай параллельно. Не останавливай чужой сервер ради порта.

Перед сдачей перечитай diff по `tech.md` §13.3–13.5, проверь права, изоляцию,
ценовые проекции, аудит, контрактные тесты, идемпотентность и путь ошибки.
В итоговом сообщении укажи изменения, реальные результаты проверок и блокеры.
Незапущенную проверку не называй пройденной.

## История и текст

- Делай небольшие логические коммиты по ходу работы. Добавляй конкретные файлы,
  не используй `git add .` в checkout с чужими изменениями.
- Коммиты, заголовки и тела PR, комментарии кода на английском.
  Формат: `type(scope): summary`; типы `feat|fix|test|refactor|chore|docs`,
  scope `auth|catalog|request|stock|payroll|portal|crm|queue|ui|ci`.
  Summary в императиве, строчная буква, без точки, до 50 символов.
- Автор из git config: `Sobol17 <sobolinskiii@mail.ru>`. `--author` не используй.
  Без соавторов, генераторных подписей, упоминаний моделей и промптов, эмодзи.
- Комментарии объясняют причину. Закомментированный код и TODO в мёрдж не идут.
- Документация и UI по-русски. Пиши активно и конкретно, без филлеров,
  em-dash и эмодзи. Если доступен `stop-slop`, используй его для прозы.

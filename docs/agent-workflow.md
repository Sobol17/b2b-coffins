# Работа с проектом

## Карта инструкций

| Файл                       | Назначение                                            |
| -------------------------- | ----------------------------------------------------- |
| `AGENTS.md`                | Общие правила, ограничения и вход в работу            |
| `tech.md`                  | Контракты, архитектура, роли и состояние продукта     |
| `PLANS.md`                 | Когда писать план, как вести и продолжать его         |
| `src/lib/server/AGENTS.md` | Слои, транзакции, изоляция данных и очередь           |
| `src/lib/domain/AGENTS.md` | Чистота домена и инварианты                           |
| `src/lib/ui/AGENTS.md`     | Примитивы, токены и ограничения сборки                |
| `src/routes/AGENTS.md`     | HTTP, формы и серверные границы                       |
| `tests/AGENTS.md`          | Критерии приёмки, фикстуры и безопасность тестовой БД |
| `docs/AGENTS.md`           | Владение документацией и исторические материалы       |

Codex читает цепочку `AGENTS.md` от корня до рабочего каталога. При старте
из корня вложенные файлы для затрагиваемых путей нужно прочитать перед правкой.
`PLANS.md` и это руководство загружаются по ссылкам из корневых инструкций.
Механика описана в [официальной документации](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

Проект не требует Claude Code, отдельной подписки на него или установленного
набора Superpowers. Доступные skills можно использовать по назначению.
Их команды, внутренние имена инструментов и маршруты установки не являются
контрактом проекта. Настройки модели и разрешений остаются в пользовательском
окружении; проект их не переопределяет.

## Начало и продолжение

1. Прочитай `tech.md`, проверь `git status --short --branch`, `git diff` и
   последние коммиты. Отдели свою задачу от незавершённой работы владельца.
2. Найди слайс в §14, критерии приёмки и относящийся к нему план или дизайн.
   Прочитай локальные `AGENTS.md` и эталон K5 перед правкой слоя.
3. Сопоставь нужные типы, поля, права, события и UI-пропсы с ядром.
   При CONTRACT GAP останови зависимую реализацию и дождись решения владельца.
4. Выбери отдельную ветку. Когда checkout занят другой работой, используй
   worktree. Не меняй существующие деревья и не копируй рабочие данные молча.
5. Для поведения: критерий, падающий тест, минимальная реализация, зелёный тест,
   self-review, небольшой коммит. Для документации: правка, проверка фактов,
   ссылок и формата. Гейт перед мёрджем общий.
6. При продолжении плана проверь сделанное по коду и git. Не повторяй
   реализованный слайс из-за оставленных пустыми чекбоксов.

Исследование, локальные обратимые правки и проверки внутри поставленной задачи
не требуют повторного подтверждения. Неописанные продуктовые решения выноси
владельцу. Публикация, мёрдж и деплой выполняются в рамках его запроса.

## Локальный запуск

Нужны Node.js 22 или новее и pnpm 10.11.0 (`package.json`). CI использует Node 22.
Установи зависимости `pnpm install --frozen-lockfile`. Для e2e один раз выполни
`pnpm exec playwright install chromium`; на Linux могут потребоваться системные
зависимости: `pnpm exec playwright install --with-deps chromium`.

Скрипты CLI читают экспортированное окружение через `config.ts`, сами `.env`
не загружают. Для локальной работы с фейковыми драйверами в отдельном терминале:

```bash
export NODE_ENV=development
export ORIGIN=http://localhost:5173
export DATABASE_PATH=./data/app.db
export FILES_DIR=./data/files
export SESSION_SECRET=local-development-secret-at-least-32-chars
export MAIL_DRIVER=fake
export PUSH_DRIVER=fake
pnpm db:migrate
pnpm seed
pnpm dev --port 5173 --strictPort
```

Этот секрет подходит только для локальных фикстур. Для стенда используй его
настройки по `docs/deploy.md`. Существующую `.env` не перезаписывай.
Перед сидом или CLI проверяй целевые `DATABASE_PATH` и `FILES_DIR`.
Демо-данные добавляет отдельная `pnpm seed:demo`; гейт её не вызывает.

## Команды проверок

| Команда                                           | Что проверяет                                    |
| ------------------------------------------------- | ------------------------------------------------ |
| `pnpm lint`                                       | Prettier и ESLint                                |
| `pnpm check`                                      | SvelteKit sync, svelte-check и TypeScript        |
| `pnpm test:unit`                                  | Unit и domain, покрытие строк домена не ниже 90% |
| `pnpm exec vitest run tests/unit/profile.spec.ts` | Один тестовый файл без отчёта покрытия           |
| `pnpm test:e2e`                                   | Полный Playwright на production bundle           |
| `pnpm test:e2e tests/e2e/crm-shop.e2e.ts`         | Один сценарий Playwright                         |
| `pnpm build`                                      | Production bundle `adapter-node`                 |

Для сборки экспортируй `SESSION_SECRET` длиной от 32 символов и фейковые
драйверы, если не используешь терминал из примера выше. Не печатай секреты.
Наличие команды в документации не означает, что она уже выполнена.

Unit setup изолирует БД каждого файла теста. Playwright хранит отдельные данные
в `data/e2e.db` и `data/e2e-files`, мигрирует их до старта сервера, затем запускает
общий сид в global setup. Этот файл нельзя удалять при работающем сервере.

Порт 4173 должен быть свободен. В обычном локальном запуске Playwright может
переиспользовать сервер; для воспроизводимого гейта используй
`CI=1 pnpm test:e2e --reporter=list`, чтобы поднимать собственный сервер.
Если порт занят, выясни владельца и используй свободное окружение; не убивай
процесс вслепую. Сборка и e2e меняют общий `build/`, запускать их параллельно нельзя.

## Полный гейт перед мёрджем

Порядок соответствует `tech.md` §11.1 и ручному `.github/workflows/ci.yml`:

```bash
pnpm install --frozen-lockfile
pnpm lint
pnpm check
pnpm test:unit
CI=1 pnpm test:e2e --reporter=list
pnpm build
```

Дополнительно проверь миграции и сид на чистой временной БД и health именно
через `node build`. Следующий блок выполняется после сборки, в subshell,
чтобы тестовое окружение не заменяло настройки текущего терминала:

```bash
(
  set -eu
  gate_dir=$(mktemp -d)
  server_pid=
  cleanup() {
    if [ -n "$server_pid" ]; then
      kill "$server_pid" 2>/dev/null || true
      wait "$server_pid" 2>/dev/null || true
    fi
    rm -rf "$gate_dir"
  }
  trap cleanup EXIT
  trap 'exit 130' INT
  trap 'exit 143' TERM
  export NODE_ENV=production
  export PORT=4174
  export ORIGIN=http://localhost:4174
  export DATABASE_PATH="$gate_dir/app.db"
  export FILES_DIR="$gate_dir/files"
  export SESSION_SECRET=local-gate-secret-value-at-least-32-chars
  export MAIL_DRIVER=fake
  export PUSH_DRIVER=fake
  export LOG_LEVEL=warn
  pnpm db:migrate
  pnpm seed
  node build >"$gate_dir/server.log" 2>&1 &
  server_pid=$!
  ready=
  for attempt in $(seq 1 30); do
    if ! kill -0 "$server_pid" 2>/dev/null; then
      cat "$gate_dir/server.log"
      exit 1
    fi
    if curl -fsS "$ORIGIN/api/health"; then ready=1; break; fi
    sleep 1
  done
  test "$ready" = 1
)
```

Порт 4174 тоже должен быть свободен. При проверке изменения схемы дополнительно
прогони миграции на копии дев-базы (§13.5), сохраняя исходник.
Если проверка упала, запиши команду и причину, исправь в рамках задачи и повтори
затронутые проверки. Полный гейт не считается зелёным при пропуске шага.

## Self-review и сдача

- Сверь итоговый diff с критериями, §13.3–13.5 и исходным объёмом задачи.
- Проверь права каждого действия, row-level, ценовые DTO, аудит, историю,
  идемпотентность, путь ошибки и отсутствие новых контрактов вне ядра.
- Для UI проверь роль и чужую роль, телефон и production bundle.
  Приложи результат наблюдения, если он нужен для оценки изменения.
- Посмотри `git diff --check` и список staged-файлов. Не добавляй чужие файлы.
- Сделай коммит по соглашению. PR описывает поведение и доказательства проверки;
  шаблон лежит в `.github/pull_request_template.md`.
- Итог владельцу: что изменилось, где, какие команды прошли, что осталось.
  Не называй CI пройденным, если выполнялся только локальный гейт.

## Поддержка харнесса

Меняй правило там, где им владеют: бизнес-контракт в `tech.md`, общий рабочий
процесс здесь, локальное ограничение в соответствующем `AGENTS.md`, формат
плана в `PLANS.md`. Контрактная правка требует бампа ядра.
Ссылки в исторических планах можно чинить, не переписывая их результат.

Локальный `.claude/` может содержать старые worktree. Он остаётся игнорируемым
и не участвует в запуске. Удалять дерево можно только после проверки его
изменений и по отдельной задаче. Аналогично `.superpowers/` не является исходником.

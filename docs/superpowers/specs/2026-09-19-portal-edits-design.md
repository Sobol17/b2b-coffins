## Принятые решения

Решения приняты владельцем 19.09.2026, альтернативы записаны, чтобы к ним не возвращаться.

1. **Самовывоз выводится из системы.** Адрес доставки обязателен у любой заявки контрагента. Альтернативы «оставить самовывоз» и «адрес свободным текстом» отклонены.
2. **ФИО умершего видно всем, кто видит заявку.** Включая цеховое место C5, водителя C6 и экспорт реестра. Сужение видимости до автора и менеджера отклонено.
3. **Срок доставки жёсткий.** Замораживается на `draft -> new` вместе с ценами, после отправки не двигается. Сдвиг срока делается отменой и новой заявкой.
4. **Канал МАКС записывается в контракт сейчас, драйвер делается отдельным слайсом.** Так же, как сделано с `push` до C15.
5. **Фид уведомлений в приложении не канал, а зеркало событий.** Выключить его нельзя, личные настройки управляют только почтой и МАКС.
6. **Примеры работ берутся из каталога.** Обложки опубликованных моделей, без цен, артикулов и остатков.
7. **Блок фонда на лендинге без цифр.** Название фонда, ссылка и ставка отчисления процентом. Собранных сумм гостю нет, `charity_totals` лендинг не читает.
8. **Скидка убирается только из профиля.** Строка «Скидка по договору» в корзине и в карточке заявки остаётся.

## Контракт: заявка

### Схема

`src/lib/server/db/schema/requests.ts`:

```ts
deliveryAddressId: integer('delivery_address_id').references(() => deliveryAddresses.id),
deliveryAt: ts('delivery_at'),        // hard deadline, frozen at draft -> new
deceasedName: text('deceased_name'),
// is_pickup удаляется
```

`src/lib/types/request.ts`:

```ts
export const GUARD_CODES = ['hasAssignee', 'pricesFixed', 'fullyPaid', 'deliveryFilled'] as const;
```

### Почему колонки остаются nullable

У заявки на склад (`isStockRequest = true`) нет ни контрагента, ни адреса, ни умершего. Пометить колонки `notNull` можно было бы только фиктивными значениями для складских заявок, а это ложь в данных. Обязательность выражает guard `deliveryFilled` на переходе `draft -> new`:

- заявка с `counterpartyId != null` проходит переход, только когда заполнены `deliveryAddressId`, `deliveryAt` и `deceasedName`;
- заявка на склад проходит переход всегда, guard к ней не применяется.

Guard живёт в `lib/domain/request`, значит проверяется property-based тестами по всем парам §6.2, а не только на счастливом пути.

### Форма и валидация

`draftDetailsSchema` в `lib/validation/request.ts` теряет поле `delivery` с вариантом `pickup` и получает:

- `deliveryAddressId`: обязательный идентификатор из `delivery_addresses` своего контрагента;
- `deliveryDate` и `deliveryTime`: дата `ГГГГ-ММ-ДД` и время `ЧЧ:ММ`, схема собирает из них `deliveryAt` в зоне `org.timezone`;
- `deceasedName`: строка от 1 до 200 символов после `trim`.

Черновик сохраняет частично заполненные поля, отправку блокирует сервер. Так контрагент собирает заявку в несколько заходов и не теряет введённое.

### Экран корзины

Панель отгрузки вместо переключателя «адрес или самовывоз» показывает четыре поля: адрес списком, дату на `DatePicker`, время и ФИО умершего. Все четыре помечены обязательными. Комментарий остаётся необязательным.

Карточка заявки `/portal/requests/[id]` показывает адрес, срок доставки и ФИО умершего в параметрах отгрузки. Строка «Самовывоз» из разметки уходит.

### Персональные данные

`requests.deceased_name` это персональные данные третьего лица. В §12 добавляется правило: поле не подставляется в шаблоны уведомлений и не уходит в SSE. В карточку, реестр и XLSX-экспорт реестра оно попадает, потому что решение 2 это разрешило.

## Контракт: уведомления

### Каналы

`src/lib/types/notifications.ts`:

```ts
export const NOTIFICATION_CHANNELS = ['email', 'push', 'max'] as const;
export const LIVE_CHANNELS = ['email'] as const satisfies readonly NotificationChannel[];
```

Значение `max` входит в enum колонок `notification_templates.channel`, `notification_rules.channel`, `user_notification_prefs.channel` и `notifications.channel`, показывается в матрице и в форме личных настроек. В `LIVE_CHANNELS` оно не входит, поэтому `notification.fanout` строк по нему не создаёт до C16.

Привязка пользователя к чату МАКС в контракт сейчас не заводится: колонка простояла бы мёртвой до C16. Разрыв поднимается в начале C16.

### Фид

`src/lib/server/db/schema/notifications.ts`:

```ts
export const notificationFeed = sqliteTable('notification_feed', {
  id: pk(),
  userId: integer('user_id').notNull().references(() => users.id, { onDelete: 'cascade' }),
  eventKey: text('event_key', { enum: EVENT_KEYS }).notNull(),
  entityId: integer('entity_id').notNull(),
  readAt: ts('read_at'),
  createdAt: createdAt()
}, (t) => ({
  userIdx: index('feed_user_idx').on(t.userId, t.createdAt),
  uq: uniqueIndex('feed_uq').on(t.userId, t.eventKey, t.entityId)
}));
```

Отдельная таблица, а не колонка `readAt` у `notifications`: одно событие даёт строку на каждый канал, и колокольчик показал бы одно и то же дважды. Уникальный индекс `(userId, eventKey, entityId)` даёт идемпотентность `notification.fanout` без дополнительного кода: повторный прогон джоба упирается в индекс.

`notification.fanout` пишет строку фида каждому адресату события в той же транзакции, в которой создаёт строки `notifications`. Адресаты считаются той же матрицей §7.3, но без учёта каналов и личных настроек: фид выключить нельзя.

### Колокольчик

`ContourShell` получает проп `bell: { href: string; unread: number }` рядом с существующим `cart`. Непрочитанное считает `+layout.server.ts` портала одним запросом.

Клик открывает список последних десяти событий: подпись события, номер заявки, время, ссылка на карточку. Под списком пункт «Все уведомления» ведёт на `/portal/profile/notifications`. Открытие списка помечает показанные строки прочитанными.

Живого обновления счётчика по SSE в этой правке нет. Топики §7.4 это `charity` без ПДн и `requests` только для CRM, персональный топик потребовал бы авторизации потока на пользователя. Это отдельная задача, и пункт 5 её не требует: счётчик обновляется на переходе между страницами.

## Контракт: публичные примеры работ

Гость каталог не видит: `/api/files/[id]` требует право `catalog.read`, а §18.5 прямо запрещает публичный доступ к данным каталога. Правка 1 это правило сужает.

Новый роут `GET /api/public/works/[id]` отдаёт обложку опубликованной модели без актора. Он не трогает `requireAction` и не ослабляет существующий guard: публичная поверхность сводится к одному файлу, который читается при аудите целиком. Фото скрытой, черновой или удалённой модели отвечает 404.

`LandingService.works(limit)` отдаёт до девяти пар «идентификатор обложки, название модели». Ни артикула, ни цены, ни остатка, ни идентификатора варианта в ответе нет.

Правило §18.5 переписывается: гостю отдаются только обложки и названия опубликованных моделей, счётчики каталога и остатка по-прежнему нет.

## Лендинг

`LandingWorks.svelte` встаёт между «Ассортимент» и «Производство»: сетка обложек с названием модели под фото.

`LandingCharity.svelte` встаёт после «Как мы работаем»: название фонда и ссылка из настройки `charity.fund`, ставка отчисления из `charity.rate_bp` процентом, текст о проекте. Собранных сумм и счётчиков гостю нет.

Обе секции собираются из примитивов `lib/ui` и токенов палитры «Ангел» §18.2.

## Профиль контрагента

`CounterpartyOverview.svelte` теряет карточку «Реквизиты» целиком и плитку «Скидка по договору». Ряд показателей становится двумя плитками, «Задолженность» и «Закупка за год», на `sm:grid-cols-2`.

`CounterpartyCardDto` теряет `legalName`, `inn`, `kpp`, `address`, `phone`, `email`, `settlementScheme` и `discountPercent`. Репозиторий перестаёт их выбирать. Из `portal/search/portal-sections.ts` уходит ключевое слово «реквизиты».

Поля остаются в таблице `counterparties` и в карточке контрагента CRM (C3). Убираем показ контрагенту, а не данные.

Строка «Скидка по договору» в корзине и в карточке заявки остаётся: правка 8 говорит только о профиле.

## Тесты

Контрактные:

- payload `notification.fanout` против Zod-схемы §7.2;
- тело ответа `/portal/profile` не содержит ключей `legalName`, `inn`, `kpp`, `address`, `phone`, `email`, `settlementScheme`, `discountPercent`;
- `/api/public/works/[id]` для гостя на скрытую модель отвечает 404, на опубликованную отдаёт файл.

Идемпотентность:

- `notification.fanout` дважды с тем же payload даёт одну строку `notification_feed` и один набор строк `notifications`.

Property-based, `lib/domain`:

- guard `deliveryFilled` на всех парах переходов §6.2: заявка контрагента без любого из трёх полей не проходит `draft -> new`, заявка на склад проходит всегда;
- срок доставки не меняется ни одним переходом после `new`.

E2E Playwright:

- `cp_admin` отправляет заявку только с заполненными адресом, датой, временем и ФИО; пустое поле блокируется сервером, а не только разметкой;
- `cp_employee` видит те же поля и не видит цен;
- колокольчик показывает непрочитанное, открытие списка обнуляет счётчик;
- гость видит примеры работ и блок фонда без цифр, прямая ссылка на фото скрытой модели даёт 404.

Порог покрытия `lib/domain/**` остаётся 90% строк.

## Что эта правка не делает

- Живое обновление колокольчика по SSE.
- Драйвер бота МАКС и привязка чата к пользователю (C16).
- Согласование срока доставки между контрагентом и мастерской: срок один и жёсткий.
- Управление галереей лендинга из CRM: примеры работ берутся из каталога.
- Стоимость доставки и порог бесплатной доставки: разрыв №8 §18.6 остаётся закрытым.
